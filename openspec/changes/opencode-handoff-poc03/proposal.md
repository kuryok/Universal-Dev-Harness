2. **Gateway de Inferência com allowlist estrita de `tools` e turnos `stub` determinísticos (`udh/gateway.py`):**
   - Adicionar `allowed_tool_names: tuple[str, ...] = ()` a `GatewayConfig` (validando nomes de tools não-vazios na construção de `GatewayConfig`) com validação **fail-closed**:
     - Rejeitar campo legado `functions` (se presente e não-`None`) com `403 tools_denied`.
     - Validar tipo de `body['tools']`: se presente e não-`None` e não for `list` (incluindo `{}`, `""`, números, booleanos), retornar `400 tools_invalid`.
     - Quando `body.get('tools')` for ausente, `None` ou `[]`: permitido tanto com `allow_tools=False` quanto com `allow_tools=True` (`has_tools=False`).
     - Quando `body.get('tools')` for lista não-vazia (`has_tools=True`):
       - Se `allow_tools=False` ou `allowed_tool_names` vazia: retornar `403 tools_denied`.
       - Validar cada entrada estritamente no schema OpenAI-completions (`isinstance(entry, dict)`, `entry.get('type') == 'function'`, `isinstance(entry.get('function'), dict)`, `function.name` string não vazia; caso contrário `400 tools_invalid`).
       - Se qualquer nome de ferramenta estiver fora de `allowed_tool_names` (ex.: `webfetch`, `websearch`, MCPs, escrita/shell quando não autorizados): retornar `403 tools_denied` na entrada e auditar `tool_names` (lista ordenada apenas de nomes, sem argumentos/segredos).
     - `build_openrouter_payload(..., allowed_tool_names: tuple[str, ...] = ())` (mantendo default retrocompatível): quando `allow_tools=True` e `tools` não-vazio, **valida estritamente e levanta `GatewayError` em qualquer violação (sem strip silencioso)**, reconstruindo cada tool autorizada apenas pelos campos permitidos (`type`, `function: {name, description, parameters}`).
   - Estender o backend `stub` offline com suporte opcional a turnos determinísticos (`stub_turns`) sob lock interno, com correspondência explícita por `has_tools` (ex.: turnos `tool_calls` vinculados a requisições com `has_tools=True`, respondendo texto simples a chamadas auxiliares com `has_tools=False`, como geração de título do OpenCode), evitando corridas entre threads e permitindo que Pi 1.2.0 e OpenCode 1.18.35 executem chamadas reais de ferramentas locais no sandbox `/workspace` durante a `POC-03` sem rede nem credenciais.

4. **Seleção determinística de adaptadores (ADR-026) e Pacote de Handoff F-03 seguro contra fuga via `.git` (`udh/handoff.py`, `udh/service.py`):**

   - **Isolamento Git do Core (ADR-021 — mitigação de RCE via `.git` e contrabando via `.gitignore`):**
     - O repositório Git da execução mantém o `git_dir` **fora de `/workspace`** (domínio confiável do Core, nunca montado no contêiner do agente), operando via `git --git-dir=<core_git_dir> --work-tree=<workspace>`.
     - Toda invocação `git` do Core usa ambiente sanitizado (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`), `-c core.hooksPath=/dev/null`, `-c core.fsmonitor=false`, `-c protocol.file.allow=never`, `--no-verify` e identidade/datas determinísticas.
     - Antes de commitar ou aceitar qualquer handoff, o Core **varre fisicamente** `<workspace>` com `os.walk(..., followlinks=False)` + `O_NOFOLLOW`, rejeitando fail-closed (`HANDOFF_INTEGRITY_VIOLATION`):
       - qualquer `.git`, `.gitmodules` ou `.gitattributes` dentro de `<workspace>`;
       - qualquer symlink, arquivo especial (FIFO/socket/device) ou nome/arquivo de sombreamento proibido (`sitecustomize*`, `usercustomize*`, `unittest*`, `udh*`, `*.pth`, reutilizando a disciplina de `udh/trust_store.py`);
       - qualquer entrada Git de modo `120000` (symlink no índice/árvore) ou `160000` (gitlink/submódulo);
       - qualquer divergência entre o inventário físico completo do diretório e `git ls-files` (zero arquivos untracked, zero arquivos ocultados por `.gitignore`).
     - O `worktree_snapshot_sha256` é o SHA-256 do JSON canônico `{relpath: sha256(bytes)}` produzido pela varredura física validada em correspondência 1:1 com o `HEAD` commitado (`base_commit_sha -> head_commit_sha`).
   - **Validação fail-closed de `Checkpoint` F-03, `TrustStore` e `HandoffPacket` (`schema_version: 1`):**
     - Antes de montar ou despachar o `HandoffPacket` ao 2º agente, o Core lê SQLite v4 + Git (`--git-dir` externo) + `TrustStore` e **recusa** (fail-closed) se ocorrer qualquer condição abaixo:
       1. `run.schema_version != 4` ou `run.state != 'IN_PROGRESS'`;
       2. ausência de checkpoint (`not run.checkpoints`), checkpoint obsoleto (`checkpoint.run_revision != run.revision`) ou qualquer campo Git/snapshot `None` (`base_commit_sha`, `head_commit_sha`, `worktree_snapshot_sha256`) → `HANDOFF_INTEGRITY_VIOLATION`;
       3. `checkpoint.unknown_pendencies` não vazia → `UNKNOWN_PENDENCY_ACTIVE`;
       4. `git rev-parse HEAD != checkpoint.head_commit_sha` (incluindo simulação F-03 de crash entre commit Git e gravação do checkpoint SQLite), worktree sujo/adulterado, `.git`/symlink/arquivo ignorado ou `worktree_snapshot_sha256` divergente → `HANDOFF_INTEGRITY_VIOLATION`;
       5. qualquer `evidence_hash` do checkpoint não corresponder a uma evidência registrada para o `run_id` com `collector_route == 'TRUSTED_EXECUTOR'` **e** verificada fisicamente em `trust_store.root/evidence/<run_id>/` via `O_NOFOLLOW` com SHA-256 exato igual a `evidence_sha256` → `HANDOFF_EVIDENCE_MISMATCH`;
       6. `to_adapter` não estiver em `conformant_adapters` ou `authorize_agent_execution(..., adapter=to_adapter)['decision'] != 'ALLOW'` → recusa fail-closed.
     - O `HandoffPacket` contém exclusivamente campos autoritativos e estruturados: `schema_version`, `run_id`, `run_revision`, `checkpoint_id`, `spec_id`, `spec_version`, `ticket_id`, `last_confirmed_step`, `from_adapter`, `to_adapter`, `git` (`base_commit_sha`, `head_commit_sha`, `worktree_snapshot_sha256`, `changed_files`), `evidence` (lista compacta verificada de `evidence_id`, `kind`, `verdict`, `evidence_sha256`, `artifact_digest`, `at_version`, `summary_ref`), `task_contract` (intenção/critérios observáveis + `allowed_tools`) e `packet_sha256` (definido como SHA-256 do JSON canônico do pacote **sem** a chave `packet_sha256`).
     - Proibição programática explícita de campos conversacionais (`messages`, `transcript`, `chat_history`, `assistant_text`, `stdout`/`stderr` crus do 1º agente) no esquema do `HandoffPacket` e função verificadora `verify_handoff_packet(...)` obrigatória antes do despacho ao 2º agente (ADR-011/ADR-027).
